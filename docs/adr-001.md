# ADR-001 — Monolito modular híbrido

- Estado: Aceptado
- Versión: 1.0
- Proyecto: Portfolio — Carlos Santiago Urrego Jiménez
- Repositorio: https://github.com/CarrlosU/portfolio
- Fecha: 2026-11-09
- Decisión: Opción B — monolito modular híbrido, organizado por dominios, capas según necesidad.

## 1. Contexto

Portafolio personal Full Stack (ES/EN) que debe presentar perfil, experiencia, 4 proyectos
(DimeloIA, JumpProxy Engine, Captcha Bypass, JetX Collector), stack contextualizado,
formación, logros y contacto. Despliegue como Static Site en Render (CDN + HTTPS).
Sin necesidad transaccional ni backend en v1.

Se descarta microservicios / distribuido: complejidad innecesaria.
Se descarta clean-architecture estricta por dominio: ceremoniosa para este tamaño.

## 2. Decisión

Modular Monolith + Domain-Oriented híbrido:

- 1 repo (`CarrlosU/portfolio`), 1 app Next.js, 1 build, 1 despliegue.
- 9 dominios delimitados: identity, experience, projects, technology, education,
  achievements, contact, localization, shared-kernel.
- Capas: Presentation / Application / Domain / Infrastructure.
  Solo se materializan cuando hay responsabilidad real (ej. `contact` puede ser simple).
- Dependencias hacia adentro. Domain no importa React/Next. Infrastructure
  implementa contratos. Presentation no accede directo a Infrastructure.
- Comunicación entre dominios solo vía API pública (`@/domains/projects`),
  nunca vía `infrastructure/data` interna.

## 3. Capas

- DOMAIN: modelos, value objects, contratos, reglas. Sin React/Next/IO.
- APPLICATION: queries, use-cases, mappers, DTOs. Sin UI ni storage.
- INFRASTRUCTURE: content providers, archivos estáticos, integraciones externas.
- PRESENTATION: Server/Client Components, composición visual. Sin acceso directo a datos.

## 4. Dominios y dependencias permitidas

| Dominio | Datos propios | Puede depender de |
|---|---|---|
| identity | perfil, enlaces, disponibilidad | localization |
| experience | empresa, cargo, fechas | projects, technology |
| projects | slug, arquitectura, resultados | technology |
| technology | catálogo centralizado | localization |
| education | instituciones, idiomas | localization |
| achievements | logros, evidencias | projects, experience |
| contact | email, LinkedIn, GitHub | identity |
| localization | diccionarios, locale | shared |
| shared | tipos, UI, utils | ninguno de negocio |

## 5. Persistencia compartida

No hay DB en v1. Fuente de verdad: Git (contenido tipado versionado).

Git Repo -> Content Providers (TS) -> Domain APIs -> Static Export -> CDN

- Contratos tipados compartidos (`Project`, `ProjectRepository`, `Locale`).
- Repos de lectura; interfaces async para permitir futuro CMS/API sin romper dominios.
- Validación con Zod cuando aporte valor. TS no sustituye validación runtime.
- Proyectos referencian `TechnologyReference {id}` sin duplicar descripciones.

## 6. i18n ES/EN con rutas estáticas

- Rutas: `/es`, `/en`, `/es/projects/[slug]`, `/en/projects/[slug]`.
- `/` landing ES con acceso a EN (sin redirect dinámico, compatible con export).
- `generateStaticParams()` para 2 locales x 4 proyectos = 8 páginas.
- Contenido Server Components; selector idioma Client Component pequeño.
- `hreflang`, canonical, metadatos localizados.

```ts
export const locales = ["es", "en"] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = "es";
```

## 7. Rendering / Despliegue

```ts
const nextConfig: NextConfig = {
  output: "export",
  trailingSlash: true,
  images: { unoptimized: true },
};
```

Flujo: dev -> `npm run build` -> `out/` -> push `main` en `CarrlosU/portfolio`
-> Render Static Site (`npm ci && npm run build`, publish `out`) -> CDN/HTTPS/auto-deploy.

Sin API Routes, Server Actions, DB ni sesiones en v1. Backend futuro (FastAPI +
PostgreSQL/Redis stateless) como sistema independiente.

Escalabilidad: horizontal vía CDN en v1 (Render la gestiona). Vertical no necesaria.
Backend futuro escalaría horizontal con persistencia externalizada.

## 8. Reglas verificables

- Dominio no importa internals de otro — Obligatoria
- Presentation no accede a Infrastructure directo — Obligatoria
- Domain no importa React/Next — Obligatoria
- Shared no importa dominios — Obligatoria
- Infrastructure implementa contratos — Obligatoria
- Alias `@/*`, ESLint + Prettier, TS estricto, Server/Client separation, lazy loading.
- Sin secretos en frontend.

## 9. Testing

Vitest (unit/integración) + Testing Library (componentes) + Playwright (E2E:
navegación, idiomas, responsive). Sin % cobertura arbitrario; foco en rutas,
traducciones y componentes críticos.

## 10. Consecuencias

Beneficios: separación, bajo acoplamiento, reutilización, evolución progresiva,
despliegue simple.
Costos aceptados: disciplina de límites, duplicación ES/EN controlada,
rebuild para actualizar contenido, sin admin dinámico ni auth.
